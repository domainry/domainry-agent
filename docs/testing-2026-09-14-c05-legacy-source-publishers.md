# C05：旧来源发布角色恢复与实际提交身份

日期：2026-09-14。接续[明确来源阅读与自动交付](testing-2026-09-14-c05-delegation-source-reading.md)。本阶段继续 C05，完整清单仍为 4／25。

后续[旧接单要求根与历史分页身份](testing-2026-09-14-c05-legacy-admission-sources.md)已补齐原接单声明恢复和交付回执入口的准确用途边界，并增加约定／交付发布同时转换为旧格式的真实验证。以下保留本阶段原范围和证据。

## 实现

- 新的约定来源和交付来源保存实际提交角色，原运行角色继续单独用于结果证明。既有关系中冻结的发起／接收角色不替代本次人工提交角色；存储仍核对提交者与相应原主体的真实归属。
- 只有 `deliver` 产生交付来源发布。`review_delivery`、`accept_delivery` 和旧交付历史保留只记录评估，不新增或修改来源授权。
- 旧记录没有 `Publisher` 时，从对应委派的真实历史恢复：约定修订的准确正文／输入根与 `ChangeSource`；实际 `deliver` 的准确证据／回执和接收后台运行；消息的准确来源运行与已记录发送者。原运行账本提供不可变角色，不能用当前绑定角色或之后的验收者猜测。
- 恢复只生成读取投影，不改写旧发布 ID、旧 JSON 或不可变历史。多次可证明的发布分别形成候选，每个候选仍经过当前分享／委派／资料权限检查。扫描、候选数和来源前缀保持上限。
- 缺少可证明身份的旧记录返回拒绝，不再退回原提供者角色。人工历史只记录账号而没有角色时不能推断；明确再次 `deliver` 可保存当前实际发布角色，未知旧记录也不能绕过新角色撤权。
- 已保存约定、交付及其嵌套来源按准确委派 ID、发布用途和步骤前缀读取实际发布记录。委派内阅读工具与成果验收使用相同解析；不会因为后台任务最初绑定的角色仍有效而绕过发布者撤权。当前角色自己的原记录保持原读取策略与当前委派阅读检查。

## 验证

应用用例覆盖未知旧发布者拒绝、明确重新发布恢复、新发布者撤权、其他委派／其他用途不能代替当前发布，以及原提供者与实际读者分别保留。

存储用例覆盖实际人工交付角色、换角色评估和验收不再次发布；旧交付从历史运行恢复角色而不使用后来的执行绑定；只有评估、人工身份缺失、其他根／其他后台执行不恢复授权；明确人工重新交付；旧输入证明角色与约定变更发布角色分开；消息新旧发送身份恢复与角色矛盾拒绝。所有 DML 使用 ORM；没有新增数据库迁移。

真实 Runtime 场景先产生两份专业原结果，再通过 Agent 工具委派、分页阅读和自动交付，由账号明确验收。停止 Runtime 后，仅将该委派的真实交付发布记录转换为旧格式；原模型执行、约定和交付历史保持。重新打开后仍能读取两个准确原值；切换成果读者、只撤回实际发布角色、字段撤权、原报表角色撤权以及保存的阅读分页继续复核。约定发布记录保持新格式，不能把此场景当作旧约定明确要求根已经恢复。

最终应用／存储／SDK／传输完整检查及相关 race 通过；两项 HTTP 与四项 Runtime 场景均通过，源码摘要覆盖 68 个文件。

准确命令、原始日志、工作区和源码摘要见[本阶段证据](evidence/2026-09-14-c05-legacy-source-publishers/commands.md)。数据库覆盖 SQLite，模型为确定性 wire 夹具；不构成在线供应商模型或完整页面验收。
