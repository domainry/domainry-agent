# C05：历史约定与恢复执行身份

日期：2026-09-14。接续[原约定恢复与明确重新共享](testing-2026-09-14-c05-contract-republication.md)。本阶段处理要求变更后阅读原运行，以及管理／系统通知恢复时的原执行身份。整表仍为 **4／25**，C05 保持部分实现。

## 权限如何落在代码中

- SDK 定义 `agent.collaboration.*` 十个权限：发现、配置、发起、查看、接收、管理、沟通、执行阅读、交付阅读、共享。Runtime 每次按 Authority 的用户、工作空间与原角色重新解析 Identity，使用当前 AccessBundle 和真实委派归属等事实判定；Agent 服务再与具体委派的参与人／接收主体范围取交集。缺少策略端口或解析失败不能当作允许。
- 管理操作者、原发起主体、接收执行主体、资料原提供者、本次实际发布者、当前读者分别核对。管理权限可以改变这一项委派的状态，但不能将管理者的当前角色写成任务执行角色。接单／后台执行及恢复继续核对原配置、模型、工具和当前执行授权。
- 交付物阅读不等于专业工具执行。资料阅读仍校验准确原账本、引用前缀、用途、当前资料／字段范围和发布证明；撤回执行角色不能由管理角色替代，撤回资料访问也不能借历史记录继续阅读。明确共享绑定准确版本、摘要及 CAS，预览不授予访问；保存实际发布身份与不可变审计。

## 本阶段修复

- 历史运行使用该运行保存的约定版本。服务端核对委派及准确当前／历史 assignment、原 Brief 版本、完整 Requirements 与 InputSource，再取得该原约定的资料范围。今天的任务、要求或引用根不能替换旧运行的声明；缺少准确原版本证据、冲突或伪造版本拒绝。原提供者、本次发布者和当前读者仍按当前权限核对。
- 普通暂停／恢复控制保存原任务的 Authority。同一用户换成管理角色操作，也不能改变原接单角色；新的运行采用新约定，旧运行的约定快照保持不变。
- 恢复在状态写入之前检查实际接收主体的当前 `receive`、配置绑定、模型与约定资料。没有绑定 Agent 快照的旧任务仍通过私有端口解析原执行身份，不能直接使用当前管理者。
- 执行器在模型输入、原历史来源的扁平化复核与实际执行期间保留该运行的准确约定读取范围。不能仅在取得工具目录的局部上下文设置范围，随后把已共享的原报表结果按专业查询执行权核对。冻结工具目录与真实执行身份继续限制实际调用，不因恢复读取范围扩大调用能力。
- 系统要求变更通知按持久化的接收／发起身份路由。收件箱启动再次解析原接单主体，接收方采用原任务快照；同用户旧通知误存管理角色的情况可在重启后按原任务恢复，不能从通知头取得执行授权。实际发送人的审计不被改写。
- 跨用户要求变更查询接收方实际拥有的任务，并分别投递双方通知。旧 assignment 缺少独立记录时，公开读取和私有恢复都按执行归属找原任务，原 assignment 的发起人归属保持原值。
- 单次来源检查的不同账本／阅读分支复用已完成的准确检查，避免同一原结果被反复展开。缓存键包含读者、原账本身份、用途、发布／引用范围、继承来源身份、原始／交付阅读及工具配置；当前发布授权仍在选择原账本前检查。缓存不跨请求或模型调用，保留原遍历上限、循环检查及分用途的协作权限判断。完整场景修复前已读到报表、分析与新约定，但重复遍历耗尽原 180 秒时限，交付调用被中断；不能以提高执行预算掩盖这一问题。
- 广泛回归复现原协作验收场景的上下文超限：旧结果已压到 1 KB 预览，累计请求仍超出 64 KB。补充最后一级仅保留准确结果读取引用和实际状态／错误；原用户消息、调用参数和最新请求读取的完整页保留。修复前后的同一完整 HTTP 协作场景分别失败／通过，单位用例核对省略正文不能被标成完整、原摘要与失败状态不能变化。

## 验证与边界

应用用例核对旧运行在要求和接手记录变化后的准确原资料范围、原发布／提供角色及当前字段撤权、非法版本与根；旧无绑定任务的恢复核对原执行角色及当前资料权限。

存储用例通过真正的普通启动和收件箱启动分别核对原运行 Authority、快照与新约定版本，验证没有重复启动。三种收件箱场景为同身份接单、持久化旧管理角色通知、跨用户接单。修复前代码使用独立 Go overlay 对照，不改工作区：前两种实际启动为管理角色，跨用户要求变更报任务不存在；当前代码三种均通过。

真实 Runtime 场景从不同旧角色的实际报表／分析原回执、Agent 工具委派、分页阅读、自动交付和账号验收开始，继续核对旧格式约定恢复与重新共享，然后更新要求、重启、阅读旧页、撤回原执行角色时恢复被拒绝、恢复原角色后新运行及再次交付／验收。最终通过状态与准确日志以[本阶段证据](evidence/2026-09-14-c05-historical-contract-lifecycle/acceptance.json)为准。

本阶段使用 SQLite 与确定性模型 wire。前端没有本阶段改动；未再次声明浏览器／前端构建验收。更多旧格式历史接单与原约定缺失场景、多所有者首次共享和依赖根、其他专业资料适配、参与人更多权限范围、完整执行详情共享、跨主体转交／退出与恢复页面普通管理入口仍待完成。整个原约定记录不存在时仍拒绝，不从当前要求合成历史。

最新验证：当前源码的 8 个核心／SDK 包及针对性 2 包 race 通过；完整 HTTP 协作场景通过，耗时 24.70 秒。真实 Runtime 场景仍失败：新运行使用原角色读取两份原回执和新约定，交付调用完成，但最终生成／提交阶段在原 180 秒时限被中断（整场景 458.91 秒）。因此本阶段**未通过完整流程验收**，不声明 C05 完成，也不提高执行预算。采样及代码显示当前 Runtime 的记录策略与报表／分析来源版本复核反复构建并摘要整个 schema 快照，后续继续处理这条热点链。原样日志、源码摘要及编译前后错误路径边界见证据目录。

后续[旧生命周期正常复验](testing-2026-09-14-c05-historical-lifecycle-normal-followup.md)已取得同一完整场景退出 0（76.23 秒），并通过旧人工交付及旧约定重新共享；原 180 秒预算保持。该后续使用独立编译版本和归档，实际 race 终态另外核对，本阶段原失败记录保持。
