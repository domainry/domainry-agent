# C05：原关联查询约束参与共享阅读范围证明

接续[原查询筛选范围](testing-2026-09-14-c05-original-query-scope.md)。本阶段补关联查询本身限定的范围，完整 C05 继续待办，整表保持 **4／25**。

实际反例：原提供者可以阅读多位客户的订单，原查询只读客户 A 的关联订单，读者也只能读客户 A 的订单。旧实现没有利用关系约束，仍要求读者覆盖原提供者完整订单策略，拒绝原第一页总数和原游标续页。正向关系也存在同样问题：读者有权查看准确目标记录，原查询只可能返回这一条记录，却被完整对象策略的比较拒绝。两组反向场景及一组正向场景在补丁前实际失败。

反向关系现在从当前已验证的关系声明中取得目标外键字段，并使用原输入里的父记录 ID 作为约束。正向关系可能被改指向，因此不能将今天父记录里的目标 ID 当作原查询条件；只有原页已认证、总数为 1、包含唯一记录且没有后续页时，才从该原记录 ID 证明原查询的唯一目标。原空页没有保存足够目标证据，继续使用既有完整策略／显式筛选证明，不猜测目标。

这些约束仍经过真实查询使用的 RecordNormalizeFilterExpression，并和显式筛选一起进入已有 SDK 范围证明。原提供者策略、当前读者策略与查询常量保留独立绑定上下文，不改变实际身份或执行授权。调用前先认证原输入与完整页，当前父记录、关系字段、目标字段及逐条保存记录仍经过 Runtime 阅读边界；读取前后仍复核当前 Identity 与来源策略。原游标不授予读者实际查询能力，原数据和总数不被当前查询替换。

新增实际 ORM 场景证明：反向关系独立限定及与显式筛选合用时可读两份原页；读者只能看到首条订单时仍拒绝原总数／续页；保存订单后来离开其当前行权限时原续页被拒绝。正向关系在父记录改指向后，原目标读者仍能读原页，只有新目标权限的读者被拒绝；篡改原目标 ID、以原空页猜测目标也被拒绝。原回执字节保持。

最终完整授权宿主正常／race 各 **58 项根检查**通过，分别为 1.006 秒与 5.803 秒；七类业务原回执真实 RPC／重启根 8.88 秒、包检查 9.668 秒通过。4691 份依赖源码在这些检查后未变化，两个补丁前的生产文件、最终生产文件、新夹具与完整日志保存在[阶段证据](evidence/2026-09-14-c05-original-relation-scope/acceptance.json)。新增条件行分支由真实 Runtime RecordApplication／RecordStore／SQLite 与 SDK 身份夹具证明；未将其记作公开原生条件角色配置或实际模型新分支验收。
