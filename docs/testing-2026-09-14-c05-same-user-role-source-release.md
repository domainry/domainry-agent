# C05：同用户不同角色的明确来源发布

日期：2026-09-14。接续[报表与分析跨主体交付](testing-2026-09-14-c05-professional-source-release.md)。本阶段补齐明确绑定接收角色时，同一用户的发起角色与执行角色之间的来源发布、原证明核对和实际读者授权。**C05 仍未完整验收，整表仍为 4／25。**

## 代码与边界

- 会话、运行和配置归属继续按 Runtime／工作区／用户保存，不把角色改成另一套会话所有权。同用户不同角色的委派身份已经分别持久化，本阶段取消来源发布、消息来源和交付上下文中按用户相同直接跳过的分支。
- 发布账本从原运行读取真实执行 Authority，保留其原角色；提交引用时的当前角色不能改写原证明身份。完全相同的原执行身份与读者不创建多余发布记录。存储仍使用 ORM 和已有第 28 项 host migration，没有新增迁移或账本。
- 内部来源快照增加不进入 JSON 的原运行 Authority。来源遍历从专业执行返回发起方的原运行时，恢复该运行的角色用于账本与证明核对，实际读者始终不变。其他角色的来源需要相应明确发布；不同用户／工作区的错误快照拒绝。
- 已提交回执读取先建立受权发布上下文，再遍历来源。即使用户级存储能找到原运行，也不能把当前阅读角色误当成回执签名角色。普通执行入口继续执行其原有权限核对。
- Identity 的 effective permission 投影可能为同一操作保留不同范围／审计策略。SDK 的 FunctionGrant 不包含这些范围，本阶段按资源和操作去重功能授权，避免合法多角色权限包报 `identity.function_grant_duplicate`。DataPolicy、字段与审计策略继续分别保留；功能授权不会补出缺失的资料范围。

## 实际场景

真实 Identity／Runtime／Report／Tools／SQLite 中，同一账号先以 headquarters_admin 创建并明确绑定专业 Agent，再通过实际账号角色分配同时保留该专业角色和 a_results_reader。Identity 按当前默认角色签发页面请求身份，测试显式刷新凭证并检查当前默认角色为 a_results_reader；Agent 的执行角色仍为 headquarters_admin。

发起 Agent 发出 agent_delegate，账号完成该调用要求的操作确认；接收 Agent 以绑定的专业角色自动发现目录、查询报表和计算分析，逐行求和并比较原分析总额 70，自动交付四份原回执。发起角色没有 Report／Analysis 的执行权限，独立阅读这四份回执并通过账号 HTTP 操作验收。普通执行详情的原资料被隐藏，并返回来源权限错误；重新读取干净响应对象确认步骤未泄露，未发布调用引用拒绝。

重启后四份回执继续可读。切换到资料字段拒绝角色时四份读取拒绝；切换到 owner 行范围角色时原报表与分析结果均拒绝。两个场景保留原 a_results_reader 及 headquarters_admin 的分配，避免把原角色失效误当成实际读者的字段／行范围拒绝；恢复阅读角色后继续可读。最后移除原专业角色，四份回执均拒绝。

模型为确定性流式 wire 夹具，所有引用均来自实际返回结果，业务工具与授权 owner 均为实际实现；不声明真实模型成功率或发起 Agent 自主验收。同用户普通会话归属没有改为按角色隔离。此前跨用户专业交付及双用户时钟／执行 HTTP 场景也回归通过。

应用和存储完整包、SDK persistence／Module transport／remote／server、Identity SDK adapter 完整包通过；新增来源遍历、发布和 Identity 权限包投影的 race 检查通过。命令顺序与代码版本范围见[本轮证据](evidence/2026-09-14-c05-same-user-role-source-release/commands.md)。

## 剩余范围

本阶段验证明确绑定的发起／接收角色及已发布回执。尚未发布、又由其他旧角色产生的来源在首次共享前仍需要独立解析及当前来源授权；多角色／多所有者混合根来源继续保留在 C05。其余专业来源的跨主体阅读与自动交付、参与者管理及执行／交付范围、完整执行详情共享、跨主体转交与主体退出仍按 TODO 顺序推进。业务 RPC 摘要与公开工具 DTO 本阶段不变。
