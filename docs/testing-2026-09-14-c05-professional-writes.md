# C05：跨账号专业写入与原执行回执

接续[工作区账号来源](testing-2026-09-14-c05-shared-account-sources.md)，补 Calendar 创建／修改和 Mail 回复。C05 继续按完整要求核对，整表仍为 4／25。

三个新增场景均由实际账号确认 `agent_delegate`，配置所有者绑定自身角色接单，以独立会话执行。Identity、Integration、Connectors、Tools、原写入账本、Agent worker、HTTP 和重启均使用实际实现；外部服务和模型为协议夹具。

- Calendar 创建保留完整日程、全天日期及排他结束日期、实际邀请参数和 `created` 原回执；Calendar 修改先执行 `calendar_event_inspect`，模型从实际工具回执取得 ETag，再由账号确认准确 PATCH。检查省略与明确清空、版本前提和 `updated` 回执。
- Mail 回复读取实际原邮件，由服务适配器恢复原线程和 RFC 引用；核对 Reply-To、显式抄送／密送、完整正文及服务 `accepted` 回执，完成条件保留送达状态未知。
- 实际 HTTP 等待期间明确发布原运行，其他账号只看到公开状态和时间。Calendar 检查返回后产生的修改确认仍由实际接收账号处理，不能由共享阅读替代确认。
- 每项工具原回执分别对应完成条件。自动交付后撤回双方专业执行／账号写入权限；读者依靠当前账号阅读权限读取准确交付、完整公开执行和 256 字节结果分页，核对原 JSON 与 SHA-256，再明确验收。
- 重启、当前读者资料撤权及工作区账号撤销均重新核对；私有会话／运行／取消入口保持隔离。实际效果计数只允许对应操作一次；读取、验收及重启不产生额外厂商请求。

## 并发等待诊断

上一阶段的跨账号 MailSend race 检查在进入业务 HTTP 前结束观察。新增时间及状态记录证明：worker 约 55 秒进入待确认，实际账号确认返回时约 62 秒，业务 HTTP 尚未开始。CPU profile 中实际 Identity principal 解析、SQLite 查询及 race 运行时均有成本；不能将原因归为正文大小。

原测试把发起方委派和接收方执行合用一个 60 秒观察窗口，遗漏两个独立运行之间的接单和人工确认。现在从准确接收任务／原运行出现时另开始观察接收方；实际 SDK、宿主及持久任务预算保持 12 步、12 次调用、8192 字节输出、60 秒。worker 的原超时、当前权限和租约围栏不变；没有忽略终态错误或重发原操作。原失败日志及 profile 独立归档，不改写上一阶段证据。

进一步检查还证明，原夹具在开始厂商 HTTP 后才做共享发布，持有该 HTTP 的同时执行了额外的页面授权检查。对于先确认后写入的操作，现在在持久待确认状态发布准确原运行，再由真实账号批准；共享读者仍在实际调用被标为运行中时核对载荷隐藏。HTTP 释放后的完成观察独立开始，服务端原超时仍会终止失败运行。Calendar 修改的首个 HTTP 是只读检查，检查之后的新修改确认仍单独核对。

调整后的实际跨账号 MailSend race 仍未通过：原交付已持久保存，随后运行超时，任务记为 `execution_interrupted`。该日志记失败，未调大执行预算、未删除原交付或重复发送，也不把普通 HTTP 通过替代为 race 通过。并发性能和交付后终态的完整阅读边界继续核对。
