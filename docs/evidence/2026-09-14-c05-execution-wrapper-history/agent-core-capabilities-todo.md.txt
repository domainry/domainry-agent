## 设计约定

- Agent 具有独立身份和生命周期，角色平等；Agent、任务、委派和消息分别建模。一个 Agent 可以处理多个隔离任务，也可以向其他 Agent 发出委派。
- 委派记录发起方与接收方，关系可以形成协作网络。管理权限定在具体委派；取消一项委派不销毁接收方 Agent，也不影响其其他任务。原任务的来源关联继续用于追溯，不赋予 Agent 父子关系。
- 角色平等不代表数据权限相同。执行使用当前用户／服务主体授权、接收方能力与本次委派范围；发起方不必配置接收方全部专业工具，但必须有委派相应工作的权限。
- Agent 拥有协作、任务状态和执行记录，公共契约归 Agent SDK；工具声明与适配沿用 Tools，身份归 Identity，资料与成果归 Knowledge，连接归 Integration／Connectors，时钟与通知分别归 Scheduler／Notification。
- 第一批按现有部署边界实现，复用执行账本和 worker。跨独立 Agent 服务的通信协议在明确部署需求后扩展。

## P0：Agent 协作与委派，先交付完整页面链路

- [x] C01 **独立 Agent 与目录**：区分能力定义和可接收工作的 Agent 实例，提供稳定身份、名称、能力摘要、配置版本、启停与可接收状态；支持发现和选择获准使用的 Agent。选择时核对能力、资料访问范围、接单容量和预计成本，注明可用性依据与更新时间；结合 E05 的实际执行记录逐步改进匹配。
- [x] C02 **按 Agent 执行任务**：任务绑定接收方 Agent，每个任务保持独立上下文；冻结配置版本、模型标识和工具范围，恢复时核对版本与当前授权。扩展现有任务实现，保留已有会话和计划入口。
- [x] C03 **双向消息与运行中补充**：建立持久收件箱，标记发送者、接收者、任务／委派和消息类型；支持下一步补充、下一轮排队、问题与回复。记录送达和消费状态并去重；Agent 消息保留真实身份，不能冒充用户授权。要求变更携带任务约定版本，按 E02 识别受影响任务后定向通知，记录接收状态；未采用新要求的执行和交付必须可辨认。
- [x] C04 **委派生命周期与管理**：支持发起、受理／拒绝、等待补充、执行、交付、验收／补充工作，以及暂停、取消、恢复和失败处理。保存目标、输入、交付要求、预算与版本；变更要求需明确接收，转交需关闭或核实旧执行，避免重复效果。委派可声明结构化输入／输出 Schema，交付保存经过校验的数据、证据和成果引用；格式不合格不能标记为有效交付，格式合格仍需按 E03 核对任务完成条件。明确委派目的、该项交付负责方与验收方，职责随具体任务确定；结合能力收益和协调成本决定直接执行或委派，简单工作不强制拆分。结论分歧进入 E03 的证据核对流程，保留处理决定和后续责任。
- [ ] C05 **委派授权与资料共享**：分别定义发起、接收、管理、沟通、查看执行和读取交付物的权限；专业工具执行权与成果查看权分开。跨任务资料通过受权引用或明确共享提供，继续核对来源权限与私有附件范围。
- [ ] C06 **协作页面与实时详情**：主会话展示委派 Agent、任务、实时状态、当前步骤和等待事项；提供“我发出的／我接收的”列表。点开复用运行详情，查看公开进度、双方通信、工具参数／结果、错误、成果、引用和用量；可发消息及管理具体委派，刷新重连后恢复现场。增加统一“需要我处理”入口，集中补充问题、操作确认、结果核查和交付验收，显示阻塞对象及影响，并复用现有交互卡片完成处理。展示有证据的业务进度、阶段成果和剩余事项；步骤数与调用次数作为执行明细，不能直接换算为任务完成比例。
- [ ] C07 **异步交付与协作恢复**：委派立即返回稳定 ID；等待释放 worker，消息／交付事件唤醒任务。持久保存委派、投递、交付和验收记录，支持重启、重投去重、停止与回执竞态；限制同一工作目标的委派数量、总预算和通信频率，检测循环等待。转委派需明确策略和来源链路。语义相同且访问范围允许的补充问题可合并展示，答复关联各原始等待事项并定向传递；消费幂等并复核事项版本，已关闭或已变化的事项不得错误唤醒。操作确认继续绑定精确操作与授权范围，不能借合并问题扩大授权。

第一批完成标准：用户交给 A 一项工作 → A 分别委派给 B、C → 页面同时显示 B、C 的真实执行 → 用户或 Agent 补充要求 → B、C 交付 → A 验收并汇总。期间刷新、重启或取消其中一项，状态与已完成效果仍可核实。要求变更传播、结论冲突处理和统一待处理入口随第一批交付；同步建设 E01–E03／E06 所需的任务约定版本、依赖引用与证据核对基础，不要求一次性实现所有高级规划能力。

## P1：通用自主推进与执行效率

- [ ] E01 **持久目标与持续推进**：在现有任务目标和计划跟进上补通用 Goal 生命周期、阶段进度、未完成事项和跨轮继续机制；明确暂停、阻塞、完成及预算耗尽的处理，沿用既有后台任务与调度入口。将用户需求整理成可更新的任务约定，包含目标、交付内容及使用对象、约束、截止时间、完成条件和待核实假设；用户和受权参与 Agent 可查看当前版本。简单任务自动整理，影响执行或验收的关键歧义才询问；推定内容与用户明确要求分别记录，缺少截止时间时不自行编造。
- [ ] E02 **计划与动态调整**：持久保存步骤、依赖、输入输出、执行者和状态；根据新消息、工具结果与失败调整后续步骤，保留已完成证据和计划版本。简单请求可直接执行；规划指导与实际执行授权分别处理。建立任务要求、执行依据与成果版本的依赖引用；要求变化后判断受影响范围，暂停依赖旧要求的后续执行、通知相关 Agent，并将相关交付标记为待更新或待核实。保留历史版本和已发生效果，复用仍有效的工作；Agent 保存任务与成果引用的有效性，正文和版本继续归 Knowledge。
- [ ] E03 **完成验收与恢复决策**：把每项交付要求关联到工具回执、数据或成果版本；区分受理、执行结束、交付和验收通过。可确定验证的条件由程序检查，其他条件记录模型评估或用户决定；遗漏则续办，外部结果不明则先核查，不能仅凭 stop 标记目标完成。Agent 结论冲突时对照数据范围、时间、来源版本和计算过程，决定补查、修订或请用户判断；保存采用的结论、简明依据、未解决分歧和处理责任，不以消息先后或多数一致直接替代证据。验收核对当前任务约定，旧版本交付不得自动通过。
- [ ] E04 **受控工具并行**：先支持无依赖且明确声明可并行的读取调用，再按资源冲突规则扩展；保留调用前授权、结果有序归档、取消收敛和独立回执。多个 worker 与单任务工具并行分别计量。
- [ ] E05 **跨 Agent 预算与进度诊断**：复用当前用户／工作区容量治理，增加任务与委派汇总的模型用量、调用、耗时和预算分配；转委派不能重置预算。识别重复调用、反复修订和无进展循环，选择调整策略、等待或报告具体阻塞。按任务类型与配置版本记录委派收益、协调耗时及实际完成情况，供 C01／C04 的选择策略使用；预计成本标明依据和不确定性。进展判断关联已核实事项、阶段成果与剩余依赖，分别呈现执行活动和业务完成情况。
- [ ] E06 **长上下文管理**：在现有字节上限、摘要和结果按需读取上补模型上下文压力估计、执行中区间压缩与可恢复的溢出处理；保留任务要求、用户修正、待办事项、工具调用配对和来源复核。增加上下文来源注册、作用范围、版本、装配顺序与更新记录；项目指令、当前业务记录和文件引用分别声明可信来源，按需刷新。稳定提示词和工具定义复用前缀，按模型能力处理动态变更并记录缓存用量，不能为缓存复用绕过授权或保留已失效资料。装配当前任务约定版本、已接收的变更和未解决分歧；历史要求与被替代的成果仅作明确标记的追溯资料，不得继续作为当前执行依据。
- [ ] E07 **模型能力与请求恢复策略**：在现有三种协议适配上增加按 Agent／任务配置模型、推理档位及模型能力声明；区分上下文上限、图片支持、结构化输出和协议续接能力。对可恢复的限流、超时、网络及服务端失败做有界退避，处理 Retry-After，持久记录尝试、等待和用量；避免重复入队用户消息、复用失败流片段或重放已执行工具。模型切换需显式核对兼容性和冻结状态。
- [ ] E08 **执行生命周期扩展接口**：为输入接收、上下文装配、模型请求、工具前后、请求失败和任务结束定义公开策略端口／事件；规划、压缩、重试和观测可独立组合，声明顺序、错误处理及配置版本。沿用 Go SDK／宿主装配，授权与回执等必须执行的检查不能被扩展接口绕过；动态装卸插件在需要时另行扩展。
- [ ] E09 **会话分叉与轨迹回放**：允许从完成的稳定会话边界复制受权上下文，形成独立平权任务，用于探索另一条执行方案；来源关联只用于追溯。提供请求／上下文／工具轨迹的受控导出、查看和对照，区分展示回放、模型录制夹具回放与真实重新执行；回放不自动触发历史外部副作用。复用现有冻结模型输入、步骤和结果记录。

## P3：按实际部署与工作场景扩展

- [ ] K07 **外部 Agent 协议接入**：把其他进程／服务中的 Agent 作为平权协作方接入，通过公开适配端口或适用的 ACP／SDK 协议交换任务、通信、状态和交付。显式协商插话、取消、恢复、结构化输出和执行详情能力；不支持时明确说明，不能用最终文本冒充完整过程。保留各方身份和授权，首批本部署内协作不依赖此项。
- [ ] K08 **完整编码执行环境**：确有编码或系统操作任务时，在独立受限宿主提供文件读写／搜索／编辑、读取后修改的版本检查、持久 Shell／PTY、后台进程控制和 LSP 定义／引用导航；与 K04 程序化工具组合分别建设。页面可观察命令、进程、文件变更及结果，产物仍交给既有成果 owner 管理。

原 X03 文档格式生成、X05 桌面应用操作仍按具体产品需求排期，分别由 Knowledge 和独立桌面桥接实现。

## 验收与交付顺序

- [ ] V01 **建立核心能力场景基线**：随各批增量验收平权互相委派、同 Agent 多任务隔离、专业工具与成果查看权限分离、插话修改要求、实时执行详情、交付验收、取消／重启、循环等待及预算耗尽。与当前基础执行做相同任务／模型／预算的对照，记录完成率、遗漏、人工介入、耗时和用量；不能仅按工具存在或接口成功判断能力完成。增加受控录制的模型请求／响应回放夹具及失败注入，用于重现上下文变更、重试和协作问题；真实工具效果使用独立夹具或隔离环境验证。覆盖下表七类补充场景，将典型反馈转为可重复评估案例；记录成果采用、修改原因与配置版本，对照改进前后及其他既有场景，验证收益和退步后再调整能力配置。

建议顺序：C01–C07 完成可见协作链路 → E01–E09 强化自主推进与执行底座 → K01–K06 按使用场景扩展。首批优先覆盖要求变更传播、结论冲突处理和统一待处理入口，E01–E03／E06 的必要基础随之交付；E07／E08 的必要基础可随 C02 建设。K07／K08 由实际部署或编码需求触发。V01 随每批建设；实现继续遵守[既有 owner 边界](remaining-capability-boundaries.md)。当前共 25 项，本次七点补充纳入既有条目和验收范围，不另增任务编号；C01–C04 已验收，其余条目包含尚未完成的范围。
