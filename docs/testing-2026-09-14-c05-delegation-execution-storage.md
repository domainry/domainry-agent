# C05：委派归属与执行归属分离

日期：2026-09-14。接续[单项委派参与人与通信](testing-2026-09-14-c05-delegation-participants.md)。本轮完成双主体接单的存储基础和存储执行生命周期验证。**应用层尚未启用跨主体接单，C05 仍未整项完成，整表仍为 4／25。**

## 已实现的底层行为

- 内部 `ConversationDelegationAdmission` 可以接收由可信接单服务核准的 `ExecutionAuthority`，该字段标记 `json:"-"`，不属于浏览器或模型的委派请求。现有应用入口仍按实际调用者执行，未开始传入另一主体。
- 新增宿主迁移 **27 `delegation_execution_subjects`**，用 ORM 保存委派发起身份、执行身份以及各自选定的角色。委派、约定历史、接手记录和交付历史仍归发起方；接收方会话、任务、运行、工具账本与执行消息归实际执行用户。当前不同用户执行的内部接单要求接收 Agent 配置确实归执行用户，且已对发起方共享。
- 同一用户的不同角色也独立保存。后台任务启动、认领、暂停后恢复使用原执行身份；回复和完成通知回到原发起身份，不将执行角色带回发起方。
- 接收方通过受限的委派身份映射访问同一条协调记录；普通会话、任务、运行读取仍保持各自的用户归属。内部追溯可以跟随绑定找到原始工作目标，不赋予接收方读取原会话的普通权限。
- 收件箱按消息接收方的执行归属保存，委派通信查询合并该委派双方的收件箱。跨收件箱的精确问题回复、消费、完成通知和通知唤醒已接通；参与授权失效时仍在同一事务处理两侧待接收消息。
- 发起方对具体委派的暂停／恢复路由到已绑定的接收方任务，保持接收方角色与原累计预算。原执行租约不能在暂停后提交结果。
- 交付记录保存接收方真实操作者，验收记录保存发起方真实操作者，两侧读取同一份不可变交付历史。不同用户执行时，发起方不能冒充接收方提交交付，接收方不能借执行身份替换发起方参与名单或管理委派。
- 接单幂等摘要包含显式执行身份；重试不能更换执行用户或角色。未显式指定执行主体的既有请求继续使用原幂等契约。

## 验证范围

使用真实 SQLite 存储和仓储的任务／运行操作，验证如下情况：

1. 不同用户创建委派后，任务按接收方身份启动与认领；普通入口拒绝双方读取对方私有会话，发起方不能直接读取接收方私有任务。
2. 发起方提问进入接收方收件箱，接收方精确回复进入发起方收件箱；完成状态写回原协调记录；重建仓储后通信仍存在，完成通知按原发起身份唤醒。
3. 接收方提交交付、发起方验收，两侧历史中的实际操作者正确。
4. 发起方暂停后旧租约不能完成；恢复后实际执行用户和角色保持。
5. 跨执行归属继续委派时可以追溯原目标和上游约定，同时保留原会话的普通读取隔离。
6. 同用户不同角色分别用于执行与回调；无关用户、不同 Runtime／工作空间和改换角色的重试均被拒绝。

相关应用、存储、Module、SDK、remote、server 回归通过；上述存储边界的 race 检查通过。原共享配置及参与通信的实际 Identity／HTTP 场景继续通过。具体命令和日志见[验证记录](evidence/2026-09-14-c05-delegation-execution-storage/commands.md)。本轮没有前端变更，没有重复打包或浏览器验证。Postgres／MySQL 仅验证迁移渲染，没有实际数据库运行结论。

## 继续实现的完整链路

本轮验证不等于专业权限接单已向用户交付。后续应用层需要提供接收方明确认可的执行身份绑定，复核当前 Identity 角色、接单范围与配置版本；发起方不能通过选择共享配置直接取得配置所有者的执行权。需把接单、发现匹配、恢复和模型／工具执行边界统一接到该绑定。

委派约定、Agent 消息、执行详情和已提交交付的跨主体来源阅读仍需明确契约，保留实际读者与原执行主体分别核对。当前参与范围还是查看约定与沟通，完整的参与者管理、执行阅读和交付阅读仍待实现。

跨主体转交需要同时迁移当前执行绑定并保留逐次接手的执行证据，旧转交入口当前拒绝这种状态。主体退出／清理也需要处理双侧绑定和剩余工作。跨所有者依赖传播与全目标预算仍需与 C03／C07 的现有机制贯通。上述事项完成前不开放跨主体接单，也不将 C05 标记完成。
